Your AI agent handled the same number of tasks this month as last month, but the bill climbed from $600 to $2400. Nothing obvious changed in the dashboard. So what happened? Here is the explanation. A workflow can repeat tool calls, retry field steps, or ask another model for help. If nobody measures, the number of paid actions required for an accepted result. The budget can rise even while the workload stays flat. I will show the math, then give you three controls to put in place before an agent touches your business spending limit, and a 4T limit, and an evidence trail. The example is fictional with clear assumptions, so you can replace the numbers with your own. Start with 200 tasks per day for 30 days, that is 6 ,000 tasks. Assume each paid model or tool call costs 2 cents. The exact price is hypothetical, not a vendor quote. In month 1, each task uses 5 paid calls. 6 ,000 times 5 times 2 cents equals $600. In month 2, each task uses 20 paid calls. 6 ,000 times 20 times 2 cents equals $2 ,400. The task cannot change. The paid calls per task rose fourfold. This calculation isolates call charges. It excludes hosting, data storage, external software, integration, human review, and the cost to fixing mistakes, if those costs rise to, the total bill can be higher. The metric to watch is not only cost per watch paid calls per attempted task, cost per accepted result, and the percentage of tasks that fail are need human repair. Those three numbers expose whether your workflow is doing useful work or paying to repeat itself. There is a reason to take these controls seriously. The first control is a budget limited three levels. At the individual call level, set a maximum cost and maximum response size where the provider supports them. At the task level, limit the number of paid calls and retries. At the daily level, stop the workflow when it's approved spending allocation is reached. Suppose a task is allowed eight paid calls. If call nine becomes necessary, do not let the agent silently keep going, pours the task, log the reason and routed to a person or an approved fallback. Here is the distinction between an alert and a control. An email saying you spent too much as an alert. A budget enforcement point, the blocks, the next charge is a control. You also need a failure rule when a tool times out. The agent should not retry forever. Set a retry count, a back -off interval and an escalation path when the task fails record the failure. Do not label it as a completed result. For a small pilot, a simple ledger and a wrapper around paid tool calls or enough to test this design. Production enforcement requires reliable accounting and provided specific limits. The second control is an authority limit. A useful agent needs enough access to complete a defined job but not a limited access to the company. Take a purchasing assistant. It might read an approved supplier catalog and prepare a comparison that does not mean it should place orders, alter banking details, or approve invoices without separate authorization. Give each agent a named owner a specific job and only the permissions required for that job. Use short -lived credentials where supported. Keep payment, deletion, external publication, and other irreversible actions behind an explicit approval step. Make sure a responsible operator can revoke access. Think of the workflow as a series of gates. Read approved information. Propose a decision. Validate the proposal. Obtain approval for a sensitive action. Execute. Verify the result. A prompt that says to not spend money is not a financial control. The actual tool must enforce the restriction. A written policy helps but a block transaction is stronger evidence. The third control is an evidence trail for each run record a task identifier. Its owner. The input category. Every tool call. Cost. Retried exception. Human approval and final outcome. Do not store unnecessary personal information in the log. Protect sensitive records and define a retention period. Then create an acceptance test. If the agent extracts invoice data. Compare the fields against the checked reference. If it produces a supplier shortlist, check the requirements and source dates. If it directs an email, a reviewer proves before sending. Now calculate the metric that matters total operating cost divided by accepted outputs. Include the human review and rework costs where you have reliable data. Here is a second fictional example. An agent completes 100 tasks. But only 80 pass quality checks. The model and tool charges are $40. Human review and corrections cost another $60. They combine $100 divided by 80 accepted outputs equals $1 .25 per accepted result. If you only report 40 cents per attempted task, you hide the cost to fail results and human repair that makes the agent look cheaper than the workflow really it is. Before scaling an agent, run a control pilot with a written scorecard, pick one workflow with clear inputs and a measurable outcome. Record the manual baseline cost, elapsed time, error rate and human effort. Then run the agent on a comparable task set. Measure six items. One accepted output rate. Two cost per accepted output, including review. Three median and slow end completion time. Four tool calls and retries per task. Five unauthorized action attempts and blocked actions. Six operator time spent on exceptions. Set pass and stop conditions before the pilot. For example, stop automatically the task exceeds a paid calls if an approval is missing or if a required field feels validation. Those numbers are illustrative and should be tuned to the actual workflow. Do not calculate return on investment from time saved unless the time has defensible value. Released staff capacity is not the same thing as cash savings. Show both separately. When the pilot passes, increase volume in stages. Check whether cost per accepted output stays stable as volume grows. A quality drops or exception handling rises. Do not scale on the strength of a headline productivity percentage. Here is the decision frame work in one sentence. Do not prove an AI agent because it answers quickly. Approve it when it's cost, authority and accepted outcomes are measurable. Before your next roll out, ask three questions. What stops spending when the workflow goes wrong? What prevents an unauthorized action? And what evidence proves the task was completed correctly. If the answers are unclear, run a smaller pilot and fix the controls before giving the agent more responsibility.
